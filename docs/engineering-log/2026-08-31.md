### 2. 虚拟屏输入链路调整

虚拟屏 `Type` 改为非 IME 优先：

1. `ACTION_SET_TEXT` 写入目标节点。
2. 节点级 `ACTION_PASTE` 回退。
3. 定向 `input -d <displayId> keyevent 279` 回退。
4. 不再在虚拟屏中调用 `SilentImeController`。

同时：

- 对 Tap/Type 使用 `softKeyboardController.setShowMode(SHOW_MODE_HIDDEN)` 抑制 IME。
- 动作结束后恢复 `SHOW_MODE_AUTO`。
- `captureScreen()` 不再调用 `hideSoftInput()`，避免感知过程改变输入法状态。
- `ActionVerifier` 对 Type 优先读取执行结果的 `metadata["verified"]`。

涉及文件：

- `android/app/src/main/kotlin/com/bluewhale/agent/platform/VirtualDisplayAgentPlatform.kt`

## 三、当前仍存在的问题

### 1. 虚拟屏点击/输入时主屏仍会弹出输入法

现象：

- 虚拟屏点击输入框，或执行 `Type` 时，主屏输入法仍然可能被激活。
- 日志显示 `SilentIme restore active=false previous=null`，说明旧路径已经恢复，但真机上仍出现输入法窗口。

代表性日志：

```text
SilentIme: restore active=false previous=null
BluewhaleShizuku: Created virtual display displayId=63
BluewhaleVirtualDisplay: typeText display=63 text=生日快乐！祝你生日快乐，天天开心！ root=true lastTapPoint=(507, 2525)
BluewhaleVirtualDisplay: typeText nodeClass=android.widget.EditText editable=true text=null
```

另一个搜索场景：

```text
BluewhaleVirtualDisplay: typeText display=65 text=浏览器 root=true lastTapPoint=(620, 2473)
BluewhaleVirtualDisplay: typeText nodeClass=android.widget.EditText editable=true text=  搜索本地应用
```

分析方向：

- AOSP 明确限制：非系统拥有的虚拟屏上不会显示 IME，IME 会回到主屏或默认屏。
- 当前代码已经移除虚拟屏的 `SilentImeController` 路径，并加入 `softKeyboardController` 抑制，但仍需确认：
  1. 真机安装的是不是本轮新构建的 APK。
  2. Tap 是否在 `SHOW_MODE_HIDDEN` 生效前就已经触发 IME。
  3. 不同 ROM 对 `AccessibilityService.softKeyboardController` 的支持是否一致。
- 下一步需要把日志记录扩展为：
  - 当前 `SoftKeyboardController.showMode`
  - 主屏是否存在 `TYPE_INPUT_METHOD` 窗口
  - 点击前/后各抓一次窗口列表
  - `ACTION_SET_TEXT` 返回值和文本回读结果

### 2. 用户停止任务后，任务残留会影响下一个任务

现象：

- 用户点击结束任务后，Agent 没有可靠的终止防护。
- 上一任务的资源或运行状态可能残留，影响下一任务。

分析方向：

- 需要为每次任务增加 `runId` / generation token。
- `stopTaskRun()` 必须：
  - 取消当前 Job。
  - 等待或强制清理虚拟屏。
  - 复位 `AgentService.preview`、`state`、`pendingStart`。
  - 恢复软键盘显示模式。
  - 清空上一轮的 `lastTapPoint`、`lastLaunchedPackage`、截图缓存。
- 虚拟屏平台 `stop()` 需要幂等，并且拒绝清理期间新的动作。

### 3. 多轮对话后返回 `End of input at character 0 of`

现象：

- 多段对话后，VLM 路由或普通对话返回：
  - `End of input at character 0 of`

分析方向：

- 很可能是模型返回了空字符串、纯空白或 Markdown 包裹的无效 JSON。
- `OpenAiConversationRouter.parse()` 当前直接对清洗后的内容调用 `JSONObject(clean)`。
- 需要增加空响应保护：
  - `content` 为空时返回一个稳定的聊天回退消息。
  - 解析失败时不要抛裸异常。
  - 如果模型连续返回空响应，应提示模型异常或降级为普通回复。

### 4. 虚拟屏搜索框输入后长时间识别，且没有跳转目标应用

现象：

- 在“搜索本地应用”框中输入 `浏览器` 后，长时间停在识别屏幕。
- 之后又输入了 `q`，仍未成功跳转。
- 这段时间主屏输入法持续激活。

代表性日志：

```text
BluewhaleVirtualDisplay: typeText display=65 text=浏览器 root=true lastTapPoint=(620, 2473)
BluewhaleVirtualDisplay: typeText nodeClass=android.widget.EditText editable=true text=  搜索本地应用
BluewhaleVirtualDisplay: typeText display=65 text=q root=true lastTapPoint=(620, 2473)
BluewhaleVirtualDisplay: typeText nodeClass=android.widget.EditText editable=true text=浏览器
```

分析方向：

- `Type` 只写入文字，不负责提交搜索。
- 搜索框输入后，模型没有稳定地点击搜索结果或搜索按钮。
- 当前无进展 Wait 熔断只能防止无限空转，不能补上缺失的“提交/进入结果”动作。
- 后续建议：
  - 增加显式 `submit` / `enter` / `keyevent` 工具。
  - 或在提示词中明确：搜索框输入后必须点击搜索结果、搜索按钮或执行 Enter。
  - 对“输入后页面无变化”的任务，不要反复 Type，应反馈“未找到目标应用入口”。
